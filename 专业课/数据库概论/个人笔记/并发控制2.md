## 基于时间戳的协议

### 事务时间戳的分配

- 每个事务 $Ti$ 进入系统被分配一个时间戳 $TS(Ti)$
- 如果 $Tj$ 晚于 $Ti$ 进入系统，$TS(Ti) < TS(Tj)$
- 回滚的事务重新启动，分配新的时间戳

#### 规则

- 时间戳顺序决定了串行化顺序
- 回滚违反发出串行性操作的事务（即调度产生的结果和串行执行的结果不一致）

### 算法

- 每个数据项 $Q$ 有两个时间戳与之联系
  - $WT(Q)$: 所有执行write($Q$)的事务中最大的时间戳
  - $RT(Q)$: 所有执行read($Q$)的事务中最大的时间戳
- 同时为数据项 $Q$ 设置提交位 $C(Q)$: 表示拥有 $Q$ 上写时间戳的事务是否提交

假定事务 $Ti$ 发出read($Q$):
   1. 过晚的读 $TS(Ti) < WT(Q)$: $Ti$ 需读入的值已经被覆盖, read($Q$)操作被拒绝，回滚 $Ti$
   2. 正常的读 $TS(Ti) > WT(Q)$:
    - 若 $C(Q)$ 为真则执行read($Q$)操作，$RT(Q) = max(RT(Q), TS(Ti))$
    - 若 $C(Q)$ 为假则推迟到 $C(Q)$ 为真或写 $Q$ 的事务中止

假定事务 $Ti$ 发出write($Q$):
   1. 过晚的写: 如果 $TS(Ti) < RT(Q)$, $Ti$ 产生的值是先前所需要的值，write($Q$)操作被拒绝，回滚 $Ti$
   2. 跳过的写: 如果 $TS(Ti) < WT(Q)$, $Ti$ 产生的值已经被其后的写事务覆盖，跳过 $Ti$ 的write($Q$)
   3. 正常的写: 如果 $TS(Ti) > RT(Q) \land TS(Ti) > WT(Q)$, 则执行 $Ti$ 的write($Q$), $WT(Q) = TS(Ti)$

简单来看，时间戳协议对于每一条指令，只检查已发生的指令是否与之冲突，不考虑未来的指令。比如一条读操作，不允许读时间戳更大的事务写后的数据，因此不允许$TS(Ti) < WT(Q)$; 对于一条写指令，不允许写已经被更大时间戳事件事件读过或写过的数据。

## 有效性检查协议

规则：有效性检查协议的三个阶段

1. 读阶段：事务T在这一阶段中执行。数据项被读入并保存在T的局部变量中。所有write操作都是对局部临时变量进行的，并不对数据库进行真正更新。
2. 有效性检查阶段：T进行有效性检查，通过与其他事务的读写集合进行比较，来判定是否可以将write操作所更新的临时局部变量值拷入数据库而不违反可串行性
3. 写阶段：若T通过有效性检查，则在本阶段进行实际的数据库更新，否则回滚Tt

每个事务Tt有3个时间戳与之联系

- **Start(Tt)：** Tt开始执行的时间
- **Validation(Tt)：** Tt进入其有效性检查阶段的时间
- **Finish(Tt)：** Tt完成其写阶段的时间
    令 $TS(Tt) = Validation(Tt)$ 即等价的串行顺序与有效性确认时间戳一致

### 算法

有效性协议的检查条件：假设T1已确认，T2待确认

1. $S(T2) < F(T1) < V(T2)$: 检查$RS(T2) \cap WS(T1)$，如果为空集，则确认成功，否则可能发生冲突（比如T2先读，T1后写）。
2. $V(T2) < F(T1)$: 检查$WS(T2) \cap WS(T1)$，$RS(T2) \cap WS(T1)$。如果均为空，则确认成功，否则可能发生冲突（比如T2先写，T1后写或者T2先读，T1后写）。

## MVCC (in MySQL)

规则：InnoDB为每行数据增加三个隐藏列用于实现MVCC中的版本存储

- $db\_trx\_id$: 插入或更新行的最后一个事务的全局标识符（每个事务创建都会分配id，全局递增）
- $db\_roll\_ptr$: 指向当前记录的前一个undo log版本
- $db\_row\_id$: 行标识（隐藏单调自增id）

核心问题：哪个版本对哪个读事务是可见的？

### 算法：创建读视图

- 读视图
  - current\_trx\_id：当前事务的id
  - alive\_trx\_list：读视图生成时刻系统中正在活跃的事务id
  - min\_trx\_id：上面的alive\_trx\_list中的最小事务id
  - max\_trx\_id：读视图生成时刻目前已创建过的事务id最大值+1

- 可见性算法：
  - if db_trx_id(record_i) < min_trx_id, then record_i 对当前事务可见 (db_trx_id在当前事务之前提交)
  - if db_trx_id(record_i) = current_trx_id, then record_i 对当前事务可见 (recordi是被当前事务自身生成或修改的)
  - if db_trx_id(record_i) ≥ max_trx_id,then record_i 对当前事务不可见 (db_trx_id在当前事务之后提交)
  - min_trx_id ≤ db_trx_id(record_i) < max_trx_id: if db_trx_id(record_i) ∈ alive_trx_list, then record_i 对当前事务不可见
    - 属于则说明这条记录还未提交，对于当前操作的事务是不可见的
    - 如果不属于则说明已经提交，则是可见的

read committed 隔离性级别下，事务每次读取都会生成新的 read_view；repeatable read 隔离性级别下，事务的 read_view 始终不变。

MySQL一致性非锁定读与隔离性级别的关系：

- 在read committed和repeatable read下InnoDB使用非锁定的一致性读
- read committed的非一致性读总是读取被访问行的最新一份快照数据
- repeatable read的非一致性读总是读取事务开始时的行数据版本
